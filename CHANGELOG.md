## [Unreleased]

### Added

- Project skeleton (milestone M1):
  - Android app: Kotlin and Jetpack Compose, minSdk 29, target SDK 37.
  - Rust engine (`datapavan-engine`, `unsafe` forbidden) and JNI bridge (`datapavan-jni`).
- App audit (milestone M2, first part): every installed app with its install source, dates, dangerous permissions and special access; risk checks for VPN apps that could control the phone, preinstalled data collectors, apps that can install other apps, and sensor access; phone-wide checks for USB and wireless debugging, user-installed certificate authorities, an active VPN, an old security patch, and the bootloader and verified-boot state from hardware key attestation, decoded by a Rust parser.
- Strict sensor review: a guided pass through every app with microphone, camera or location access, which remembers what each app had when reviewed and brings it back if it gains access again; voice assistants that listen for a wake word are named, with a link to their setting; the privacy dashboard is linked on Android 12+. Preinstalled data collectors get a guide to disable them, or to remove them reversibly for the user from a computer.
- Hardware attestation is checked like a verifier on a server would: every certificate in the chain must be signed by the next, the root must hold one of Google's two attestation root keys, and no certificate may be on Google's revocation list. A revoked key or a chain that Google does not vouch for is reported. Google's roots and the revoked serial numbers ship in `data/attestation`, with their licence, source and converter.
- DEX parser in the Rust engine (milestone M3, first part): lists the classes that an app's DEX files define, for DEX versions 035 to 041, including version 041's containers of several logical files. It treats other apps' code as untrusted input, is fuzzed like every parser, and matched the SDK's `dexdump` exactly on 109 DEX files from 22 real apps (651,420 classes; `scripts/compare-dex.sh`).
- Tracker matching (milestone M3, second part): the εxodus tracker signatures in `data/exodus` (432 trackers, ODbL, with their licence, source and converter), the list of classes an app's code refers to, and a matcher in the Rust engine that finds the signatures in one pass with an Aho-Corasick automaton and tells trackers whose code an app contains from those it only refers to. Compared with εxodus reports on 22 real apps, it found every tracker that εxodus reports for the same version ([spike](docs/spikes/2026-10-m3-exodus-comparison.md)).
- Tracker scan in the app (milestone M3, third part): every installed app's code, in its base APK and every split, is matched against the εxodus signatures by the Rust engine. The overview shows the scan's progress and how many apps contain trackers; each app's page lists its trackers with their purpose, apart from those its code only refers to, and names the εxodus database and its licence. Results are cached and reused while an app and the signatures stay unchanged, and saved as the scan goes. On the A40, the first scan of 436 apps takes about two minutes, later ones seconds.
- Signed data packs (milestone M3, fourth part; [DATA-PACKS.md](docs/DATA-PACKS.md), ADR 0017): every dataset now reaches the app in a pack, a file in OpenBSD `signify`'s embedded-signature format that anyone can check with `signify -V -e`. The build makes the APK's pack from `data/` reproducibly. A *Data sources* screen shows each dataset's date and licence notice and imports a newer pack through the system file picker, without network access. The Rust engine checks the Ed25519 signature (`ed25519-compact`, the engine's first dependency) before it reads anything, the app refuses packs that are not newer, and key rotation and revocation follow a chain back to the keys pinned in the build. The screen shows the pack's SHA-256 fingerprint, which is published with every pack, and the overview warns when the data is more than six months old. The signature library is tested against Project Wycheproof's 210 Ed25519 vectors. Debug builds also trust a public test key, which `scripts/verify-datapack.sh` uses to check imports end to end on an emulator. The project's own data-signing key is still to be made offline, so release builds cannot import packs yet.
- Official signing certificates of VPN, proxy and circumvention apps (milestone M3, fifth part; ADR 0018). `data/app-signers` lists 39 certificates for 34 packages (Psiphon, Tor Browser, Orbot, Proton VPN, v2rayNG, Lantern, Hiddify, Amnezia, sing-box, Clash Meta, NekoBox, Mullvad, Signal and others), each with its source, date and evidence grade. `update.py` collects them from the fingerprints developers publish, F-Droid's metadata, repository indexes whose signatures it checks, and APKs from official channels, which it reads with `apksigner` across Android 10 to 17. Each app's page now says whose key signed it. A copy is called modified only on positive evidence: every official key known and the data fresh, or a debug key the developer never uses. A key not known yet is shown, without a warning, with its fingerprint to compare. A genuine build under another name keeps its disguise behind a tap. On an emulator, a copy of Exclave re-signed with another key is reported as modified, and so is the test fixture under Exclave's package name in CI. `data/CORRECTIONS.md` says how to dispute an entry.
- Traffic-sharing, remote-support and screen-recording SDKs (milestone M3, sixth part; ADR 0019). `data/sdks` lists 19 SDKs. `update.py` reads each identifier in the SDK its vendor publishes and records the artefact's SHA-256, and only identifiers that survive code shrinking ship: 16 for 11 SDKs, among them Pawns (traffic sharing), LogMeIn Rescue, Cobrowse.io, Glance, Zoho Assist, Upscope and ScreenMeet (remote support), and Microsoft Clarity, Datadog, LogRocket and Contentsquare (screen recording). Bright SDK, Massive, Honeygain, Repocket, TeamViewer and Unblu wait until an official artefact or app is read. The tracker scan finds them in the same pass, and each app's page states what was found, what the code does when it is on, what Datapavan cannot check and the vendor's own safeguards, without judging intent or consent. Malformed signature data no longer stops the scan.
- Completions of milestone M3:
  - The scan also matches SDKs by the names of their native libraries, which class names alone would miss. Pawns' `libpawns_ndk.so` ships.
  - The certificate collector checks detached OpenPGP signatures with the key whose fingerprint the developer publishes, which raises v2rayNG and Mullvad to grade 3.
  - It reads a second official channel where one exists, so Lantern's GitHub and website copies now agree (grade 4). It also reads the newest file from a download listing, which adds WireGuard.
  - A [spike](docs/spikes/2026-10-key-rotation.md) on Android 11 and 17 confirms that a phone may show either key of a developer who rotated keys, so the list keeps every key `apksigner` reports. Hybrid signing for Android 17 still needs a Play-signed sample.
  - Google Play copies are read too: `from-play.sh` installs each listed app from Play on a test device on which someone signed in, copies its APK and uninstalls it, and `update.py --read-play` records the certificates and signature schemes in `play.tsv`. On Android 17, 23 Play copies were read. 15 carry a key already known from another official channel, which raises six keys to grade 4. 8 carry only a key not seen before, which Google holds for Play App Signing (Windscribe, Mullvad, Outline, Amnezia VPN, WG Tunnel, Tor VPN, Happ, and InviZible Pro's Play build, added to the list). Hiddify's Play copy shows a real rotation: Android 12 and older see a key Google made, newer versions the developer's own. None carries Android 17's hybrid signature yet. The other listed apps are not offered to that device: some are not on Play, some not in the account's country, and Shadowsocks and Defyx not for Android 17. On the same emulator, the official Proton VPN APK re-signed with another key is reported as a modified copy, and LogMeIn Rescue and Zoho Assist from Play show their remote-support SDKs.
  - `scripts/compare-exodus.sh` checks the tracker scan against εxodus reports for the same app versions, on a device signed in to Play. For 16 popular apps it found every tracker in the reports, which with the six of the first comparison meets M3's definition of done (22 apps).
- A lighter, faster tracker scan. DEX files that an APK stores uncompressed, which are most of them, are mapped from the APK as Android itself does, instead of being read into memory: only the pages the parser needs are read, and they stay in memory that Android can reclaim. Each class name is decoded into one reused buffer and matched once, for the classes an app defines and those it refers to, without building lists of names. The engine scans DEX files 2.5 times as fast. The first scan of the A40's 436 apps takes 83 to 86 s instead of 119 to 122 s, with identical results for every app; there the Java heap peaks lower (48 instead of 57 MB) and the native heap, which other parts of the app dominate, stays about the same. On an Android 17 emulator the app's memory at the peak of a scan fell from 175 to 120 MB, also with identical results. Apps are scanned one at a time on low-memory and 2 GB phones, two at a time on 3 and 4 GB phones and four from 6 GB, never more than the processor has cores. A differential fuzz target checks the new reader against the old lists.
- Tracker capabilities that need a service the phone lacks (ADR 0021). `data/sdk-needs` (CC0) lists SDK capabilities that work only with a system service, each read in the vendor's own artefact (`update.py`, which records the artefact's SHA-256), and the certificates that the vendor's own client library accepts for the service. On each audit, Google Play services, the Play Store and HMS Core are judged genuine, a substitute (microG's own marks count, since it can carry Google's certificate) or absent, without any Google library. When a capability's service is absent or turned off, the app's page says so for that capability alone, for this profile and with the time of the check, and adds that the rest of the app's code can still run; findings keep their severity. Seven capabilities are listed: reading Google's or Huawei's advertising ID, push through Firebase Cloud Messaging or Huawei Push Kit, Google Play's install referrer, Play Integrity in Firebase App Check, and signing in with a Huawei account. Google's certificates come from Play services' client library, two of them rotation keys from 2020 and 2024, and HMS Core's fingerprints from Huawei's own libraries. On an emulator, the test fixture's advertising-ID class is marked only while Google Play services is turned off.
- Trackers from the app's own company group (ADR 0020). `data/owners` (CC0) records which company runs the service of 14 SDKs (Google, Meta, Microsoft, Amazon and Huawei), which company controls which, with dates and Wikidata items, and which company publishes which app by package and signing certificate. `update.py` reads publishers from the companies' own Digital Asset Links files (235 app certificates from Google, YouTube, Meta, Instagram, WhatsApp, Microsoft, LinkedIn and Amazon) and from the service certificates in `data/sdk-needs`, and checks the hand-written tables. When an app and some of its SDKs lead to the same majority-controlling parent on the data's date, the app's page names the group and adds that the group can combine this data with what its other apps and services collect; findings keep their weight, and nothing unrecorded is guessed. A service that has shut down, such as Universal Analytics or App Center, is said apart. On an emulator, the pages of Google Play services, the Google app, Maps and YouTube name Alphabet for the Google SDKs they contain.
- Network use per app and apps not opened for a long time (milestone M4, ADR 0022). With usage access, which the overview explains and asks for and nothing requires, the overview shows mobile and Wi-Fi use over the last 30 or 7 days with the apps that used the most, and the lines that Android counts under no app (removed apps, tethering, the system). Each app's page shows what it received and sent on each network, how much of it was in the background, and when it was last opened or running. Only totals are read, never which app was opened when, and nothing is kept. The pages say where Android's count needs explaining: apps that share a user ID are counted together, and traffic routed through a proxy app counts under that app. Apps not opened for 90 days that still hold a sensitive permission, special access, VPN permission or background data use are listed for the remediation plan, with a link to Android's page of unused apps; apps that work without being opened, such as keyboards and VPNs, say that this means little. Sizes use the step of the phone's own Settings, so that the two can be compared: 1,024 in AOSP, as on the Android 17 emulator, and 1,000 on Samsung phones; other vendors follow AOSP until one of their phones is measured. When Datapavan was installed from a file, Android 17 locks the usage access switch until the user allows restricted settings in the app's info, so the card explains this and opens the app's info. `scripts/compare-usage.sh` compares the numbers with Settings' data-usage screen: on the Android 17 emulator every app's mobile and Wi-Fi size read the same as in Settings, and on the A40 the ten largest Wi-Fi rows differed by at most 0.07 % ([spike](docs/spikes/2026-10-m4-network-use.md)), which meets M4's definition of done (within 5 %).
- The guided check of one activity in an app (ADR 0025). From an app's page, the user says what they will do, Datapavan reads Android's counts, opens the app, and reads again when the user returns: both readings ask for the same period, from a two-hour boundary a day before to two days after, and each comes at least 15 seconds after Datapavan's previous query, because every query restarts Android's 15 seconds before it updates its counts. The change summed over all apps is checked against the phone's live totals (`TrafficStats`), and a count that is not up to date is read again up to three times. The result shows received and sent bytes per network and per minute, the background share and, for activities that only receive, sent bytes as a share of received ones next to what acknowledgements alone take, or why that is not compared (proxy and VPN apps, shared user IDs, system components, less than 1 MB, kernels older than 4.9). A second run shows next to the first; nothing is kept. Two facts need no comparison: an app installed and never opened that used data, and background sending of at least 1 MB by keyboards, live wallpapers and home screens. No string judges an app. The method was measured first ([spike](docs/spikes/2026-11-guided-check.md)) with `scripts/traffic-lab`, a lab app and server that compare Android's counts with packet captures.
- Telegram's official keys join `data/app-signers` (ADR 0018): the website build (`org.telegram.messenger.web`), read from the APK telegram.org offers, the Google Play build and Telegram X, read from Play, and F-Droid's key for Telegram X FOSS, which uses the official package name. Fake and modified copies of Telegram spread widely, and the website build updates itself, so it holds the access to install apps. `update.py` gained `--cache-only`, which reads only files already downloaded, and keeps the date a certificate or a Play copy was first checked when nothing new was read.
- The phone maker's software and system keys that cannot be trusted (ADR 0023). The key that signs the package `android` is read on the phone, and each app's page says whether the app is signed with it, whether it runs as the system user, and whether it came with the system image, as a later update or as a later install. `data/system-keys` (CC0) lists AOSP's nine public test keys and Google's five development keys, computed from their certificate files by `update.py`, and the ten platform keys Google listed in 2022 as having signed malware. A phone whose system key is public gets a high finding, one whose key is on Google's list a medium one, and a development system a note: the Galaxy A40's system key is on the list, and the Android 17 emulator's is Google's development key. An app signed with such a key that was installed later, or updated, from anywhere but Google Play or the maker's own store is a high finding; from those stores, or put there by the phone's own setup with the phone's own key, it gets a note, since Samsung still signs its own apps with its leaked key. On the A40, no app gets the high finding. On an emulator, the test fixture signed with AOSP's public platform test key is reported.
- Permissions (ADR 0014): see all installed apps, usage access (optional, granted by the user in Settings), and network state to tell whether a VPN is active. The build fails if INTERNET is added through any build path (APK, bundle or install). Cloud backup and device-to-device transfer are disabled.
- UI in English, French, German and Persian, with right-to-left support, pseudo-locales in debug builds, and LTR token isolation.
- Supply-chain protection:
  - pinned toolchains;
  - the Gradle distribution pinned by checksum, and the wrapper jar validated in CI;
  - SHA-256 verification for every Gradle artifact;
  - exclusive repository content (Google's groups only from Google, everything else only from Maven Central);
  - a cargo-deny policy;
  - native libraries built without paths from the build machine.
- Quality gates in `scripts/check.sh`, run by CI on GitHub, including a check that every APK carries the Rust library and its JNI export, a check that every bundled dataset names its licence and source, an emulator smoke test (`scripts/smoke.sh`), an end-to-end check of the audit's findings with a test fixture app (`scripts/verify-audit.sh`), and screenshots in all four languages and both pseudo-locales with an accessibility check (`scripts/screenshots.sh`).
- Fuzzing of the attestation, DEX and data pack parsers and, against a plain search, of the tracker matcher, with cargo fuzz (`scripts/fuzz.sh`): locally, in CI for eight minutes in all when the engine changes, and for forty minutes every week, shared among the targets.
- The remediation plan for v0.1 (ADR 0026). From the overview, the user picks a light, medium or strict level and works through a session of up to five cards, those that remove the most risk first: wireless and USB debugging, certificate authorities the user installed, apps with access that can control the phone, copies that differ from the official app, apps that install apps or contain a traffic-sharing SDK, apps not opened for 90 days that still hold something, and, at the strict level, preinstalled apps. Each card opens the system screens that can remove it, Datapavan itself changes nothing, and it opens no uninstall dialog of its own, because an uninstall deletes the app's data. A care step comes first for control access, which can alert someone who installed an app to watch the user, and for preinstalled apps, which Datapavan has not tested on the phone. A safety floor leaves alone the apps the phone needs: default apps, keyboards, screen readers in use, device owners, the installer and permission controller, and a deny-list by function in `data/remediation/floor.tsv` (CC0, 41 rows with their sources). A journal records what each card actually changed, says when a change has come back, offers undo through the same screen, and asks once, three days after a session, whether everything still works; it stays on the phone and is deleted in one tap. `scripts/verify-plan.sh` checks it end to end, also in CI.
- The brand theme in the app: lapis, clay and gold in light mode, light lapis, light gold and night in dark mode, instead of the wallpaper's colours, with every text colour at 4.5:1 or more on every surface (WCAG AA), checked by a unit test, and the window's background in the same colours before the app draws.
- A plain-language check of the English strings (`scripts/plain-language.py`, part of `scripts/check.sh`): every string of twelve words or more must reach a Flesch-Kincaid grade of 10 or lower. Four strings were rewritten to pass.
- Brand: the Old Persian sign DA as the product mark and app icon, the DAHYĀUŠ logogram for the foundation, a palette with measured contrast ratios, and avatars.
- Documentation: design, roadmap, names, brand, VPN design, restricted regions, foundation charter, security policy, contributing guide (with the AI-assistance rules), privacy policy, code of conduct, and architecture decision records, including the licence check of every planned dataset (ADR 0015) and the decision to collect no data from users (ADR 0016); the design of the remediation plan.

- Release builds of the Rust engine keep integer-overflow checks.
